# 保留行为的芯片改型迁移

使用现有检索、文件、命令和验收工具完成迁移。下述内容是任务指导，具体调查和修改由你根据工程决定；它不限定支持的芯片、外设或工具调用顺序。

## 先确定保留什么、允许改变什么

- 阅读源模块的公开接口、实现与调用方，确认返回值、忙状态、结果消费、缓冲策略、中断与时序要求。直接沿用已经满足需求的算法和状态机，避免将迁移变成重新实现。
- 分别确认源芯片/版本、目标芯片/版本、封装、系统时钟、参考电压与逻辑端口。明确源工程和目标工程的位置、允许编辑的文件、需要保留的功能。缺失且会影响实现的条件才向用户澄清。
- 用一个简短的迁移说明记录“需要保持的行为”和“需要适配的硬件配置”。保存到工程中，并随实际发现更新；不要求建立新的配置语言或代码生成器。

## 对照资料定位差异

- 分别用 search_spec 查询源和目标，跨型号查询显式填写 product 和 version；版本值按检索服务返回的元数据使用。用 read_context 展开影响实现的证据，保留 document_id、chunk_id、页码、型号和版本。
- 核对实际用到的寄存器位含义、时钟来源与分频、通道/引脚复用、使能与复位行为、数据对齐、中断条件，以及当前工程的 SDK/编译器约定。同名寄存器不代表含义一致，也不因型号变化就假设所有字段都不同。
- 可以读取官方目标例程补充接线和语法。用户提供的业务行为是迁移契约，官方例程中的阻塞循环、默认频率或引脚不能覆盖它。
- 区分逻辑端口、ADC 等外设通道与封装物理脚号；没有可读证据支持物理脚号时保留未确认状态，继续能确定的开发。
- 对频率、误差、采样时长和数值上限运行计算，说明采用的时钟前提。迁移说明以“差异、依据、源码改动、对应检查”关联这些结论。

## 在目标工程中适配

- 使用通用读写编辑工具迁移实际源代码，保留用户指定的接口和业务算法。按需要调整硬件相关部分、平台头文件、初始化/轮询/中断入口及工程文件列表。
- 保留目标工程已有的系统初始化、时钟设置、共享中断分发与业务；读取实际资源占用，不通过删除旧功能解决冲突。确有不可兼容的约束时给出依据与可选择的改动。
- 有 demo-project.json 时同步受影响模块与资源，再调用 check_project_manifest。迁移完成后的记忆应注明目标适用范围，不能将源芯片的配置无范围地写回项目事实。

## 用同一份行为要求验收

- 优先运行工程已有或宿主配置的 verify_project。能执行源与目标时，用相同的行为检查比较接口、状态转换、数据结果和错误边界；芯片配置的预期值分别核对各自资料。
- 同时检查目标工程原有功能。检查失败后按实际输出定位和修复；不改变独立判据来获取通过，也不只证明“与自己写的计算一致”。
- 完成源码修改后再检查最终版本。用 record_implementation（可用时）关联配置理由、源码行、规格引用和本轮检查调用。
- 交付说明接口与行为保留情况、硬件配置差异、实际检查结果和未确认项。主机侧行为检查、厂商编译和板卡运行分别报告，不把它们互相替代。
