# 工程内的可复用模块开发

使用当前可用的工程、规格检索、官方例程和命令工具完成开发。根据实际工程选择步骤与实现，不限定芯片、外设或模板。

## 确认需求与工程约束

- 先读工程入口、已有模块及项目设置，复用已知的型号、版本、时钟和编译约定。需求足够就开始；只询问影响实现的缺失条件，不要求用户重复确认已有信息。
- 明确模块的公开接口、输入输出、阻塞或非阻塞行为、错误与忙状态，以及要保留的旧功能。查询现有引脚、定时器和中断占用，不能通过删掉旧模块解决冲突。
- 按需要读取官方例程与规格，使用 search_spec 和 read_context 保留文档、片段、型号、版本与页码。只用例程解释实现方式，用户要求决定业务行为。
- 对分频、频率、波特率、误差和数值范围运行计算。区分规格明示、计算前提与未确认事项，不用模型心算替代可执行计算。

## 实现并接入当前工程

- 使用通用文件工具编写或修改实际模块；已装配的生成工具可以作为捷径，未列出的模块照常研究与实现。
- 接好初始化、主循环轮询、必要的中断分发与调用方。保留系统初始化、时钟设置、共享入口和无关业务，避免阻塞已有运行流程。
- 同步工程文件表、头文件、模块说明；存在 demo-project.json 时同步模块、资源与实际参数，再用 check_project_manifest 核对。
- 优先复用已有计算与检查脚本；不要重复创建功能相同的自检工程。

## 检查与交付

- 运行工程已有或宿主配置的检查。verify_project 可用时，在最终修改后执行；根据真实失败输出修复并复验，不修改独立判据以取得通过。
- 检查新模块的正常、边界、重复调用与错误行为，并回归受影响的旧模块。仅与自己写的配置计算一致，不足以证明业务正确。
- record_implementation 可用时，批量关联关键实现的需求、理由、实际源码、已获得的规格依据和检查调用。
- 交付公开接口、接入位置、实际参数及检查结果。主机行为检查、厂商编译和板卡测试分别记录，未执行的检查不写成通过。
