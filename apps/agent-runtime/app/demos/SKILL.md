# 模块化 Demo 生成

目标：根据工程师的功能需求，以已审查官方例程生成可组合的模块和示例工程。

1. 先用 list_demo_modules 查看已支持型号、参数和来源，用 inspect_demo_project 读取当前模块及保留资源。
2. 采用用户本次明确输入；缺少选型/关键条件时先澄清，不从其他型号记忆推断。没有特别要求时可使用目录中明确标注的官方默认配置，并说明采用了默认值。
3. 已审查模板覆盖的需求可调用 generate_demo_module，完成共享入口组合和定时器/引脚检查；更新只传变更参数即可，其余配置保留。超出模板参数或已有定制改动时，使用通用文件工具，结合规格书与官方例程自行实现；不要把模板拒绝当作整个Agent不能开发。无需上传、下载、解压或启动另一个服务。不能仅输出一段代码后声称工程已经生成。
4. 出现资源冲突时读懂工具返回的资源与占用者，提出调整模块、端口或保留资源的选项。不得擅自释放用户保留资源；用户确认前不自动替换已有功能。
5. 连续生成多个模块使用同一个项目，不建立多个互不兼容的 main。模块提供 Init/Poll/Interrupt 等明确挂接点；用户要求业务接入时，可用通用工具实现并验证。
6. 完成后报告实际目录、模块接口、所用逻辑端口、请求值与寄存器量化结果，提供来源与集成说明。入口所在文件按工具返回的integration字段说明，不凭文件名猜测。区分结构检查、厂商编译和实机运行；没有运行的检查不标为通过。
7. 官方例程版本与规格书版本分别记录。工具目录表示已审查模板范围；自主开发时可用list_official_examples/read_official_example读取其它官方源码，用RAG补查技术依据，再用通用工具实现和验证。不能编造厂商API，也不能把新写的代码直接宣称为已审查模板。
   工具目录不是芯片完整外设清单：未适配不等于硬件不存在；不能据此断言芯片只有TC0/TC1或没有其他定时器。
8. 资源冲突时，先核对“全部保留”是否可行。区分软件节拍与独立硬件定时器：1ms节拍累计10次可形成10ms软件任务；只有10ms事件时不能靠计数提高为1ms。软件计数需要业务逻辑，模板不自动实现；自主方案可用通用工具实现，需核对原时基、精度及丢事件风险。
9. 清单 demo-project.json 属于交付内容：新增或修改生成文件后，把文件写进 managed_files，并更新受影响的 actual、入口字段和工程文件表；交付前调用 check_project_manifest。返回 ok=false 就按 detail 修正代码或清单再重跑，不能用“已同步”之类的说明代替检查结果。

## 已有工程（mode=existing）

- inspect_demo_project 实际读取 .prj 和源文件，返回入口、时钟与寄存器引用位置。read_project_file / search_project 用于核对相关代码，不能将旧记忆当作当前文件。
- 先核对 main、原有初始化与资源使用。模板覆盖时可用 preview_demo_integration 看差异，再用 generate_demo_module 写入；自主实现时使用通用编辑工具，保留原入口并检查实际差异。只要求分析时不写入。
- 模块放在 agent_demo/，保留原系统初始化、业务代码和中断处理，仅插入挂接调用、追加工程文件条目。原有文件副本路径在backup字段，写入差异在changes字段。
- 遇到冲突或无法识别的工程结构，说明工具给出的文件/行号及原因，不通过释放已有资源、改变时钟或替换整个main绕过。
- 直接寄存器扫描不是完整C语义分析；工程选项或时钟未确认时不猜。当前接入范围由工具返回，不扩充为任意固件工程均能自动集成。
